# OPENTMF-LIBRARIES.md — capability quick reference

What the shared `opentmf` libraries (`~/prj/opentmf`) provide and how to wire them, so you can pick the
right one without reading their source. **Rule:** whenever possible reuse these instead of hand-rolling
HTTP, persistence, locking, auth, serialization, or query handling.

All artifacts are version-managed by the **opentmf-versions BOM** — import it once and omit `<version>`
on individual deps. Source of truth is the code on each repo's `develop` branch; this file is a summary.

> **Last verified against BOM `opentmf-versions` 2.1.43 (2026-10-21).** Put the BOM
> version you checked against here on every refresh — it is the one fact that tells a
> reader whether this file is current, and it is checkable in one glance against the
> BOM's own version.
>
> **⚠ Do not restate library VERSION NUMBERS in the prose below.** The BOM is their
> single source of truth; a number copied here is a cache with no invalidation and it
> will drift. Version numbers appear here only where they mark *when a behaviour
> changed* ("since 2.1.6…", "2.2.0 fixed…") — that is history, which the BOM does not
> carry. What this file is FOR is the behaviour, the wiring and the **gotchas** — none
> of which live anywhere else.
>
> **Refreshing this doc.** It's a hand-built summary, not generated — regenerate it whenever the
> libraries change (new module, new config key, new bean, removed capability). Each folder under
> `~/prj/opentmf` is its own git repo; skip `retired/` and non-git folders (`code-generators/`,
> `opentmf-compose/`). Procedure: for each library repo, ensure it's on `develop` and `git pull`,
> then re-inspect `pom.xml`, `META-INF/spring/...AutoConfiguration.imports`, `@ConfigurationProperties`
> classes (prefixes + default values), exported public beans/annotations/utils, and `README.md`.
> Keep every entry in the fixed template (**What · Use it for · Key API · Config · Snippet · Gotchas ·
> Maven**) and verify names against the actual source — don't guess. An AI agent can do this by
> fanning out one inspection task per library group and reassembling the entries.

## Core & serialization

### opentmf-versions
**What:** A pom-only Maven BOM pinning compatible versions for the whole `org.opentmf.*` family.
**Use it for:** Any project consuming opentmf libraries — import once, never set opentmf versions on deps.
**Key API:** `<dependencyManagement>` import; no code.
**Config:** none.
**Snippet:**
```xml
<dependency><groupId>org.opentmf</groupId><artifactId>opentmf-versions</artifactId>
  <version>2.1.x</version><type>pom</type><scope>import</scope></dependency>
```
**Gotchas:** Pin a fixed version. 2.x = Spring Boot 4 + Jackson 3; 1.x = Boot 3.5 + Jackson 2. Overriding a BOM-managed version defeats the purpose (do it only for a CVE, with a comment).
**Maven:** `org.opentmf:opentmf-versions` (the BOM).

### opentmf-commons
**What:** Dependency-light utilities: a preconfigured Jackson 3 mapper, on-demand validation, and security-hardening field annotations.
**Use it for:** JSON (de)serialize/merge/convert, ad-hoc validation without a Spring context, hardening TMF DTO fields against injection.
**Key API:** `JacksonUtil` (`defaultMapperBuilder`, `getDefaultJsonMapper`, `setDefaultJsonMapper`, `objectToJson`/`jsonToObject`, `objectToTree`/`treeToObject`, `convertValue`, `merge`, `objectToMap`); `ValidationUtil.validate/ensureValid`; `ListUtil.safe`; annotations `@Required`, `@SafeText`, `@SafeId`, `@SafeJsonPath`, `@SafeUrl`.
**Config:** none — no autoconfig. Wire the mapper yourself in a `@Configuration`.
**Snippet:**
```java
var mapper = JacksonUtil.defaultMapperBuilder().build();
JacksonUtil.setDefaultJsonMapper(mapper);   // sync static helpers to your mapper
```
**Gotchas:** `defaultMapperBuilder()` ignores `spring.jackson.*` by design. Expose the bean as `JsonMapper` (not `ObjectMapper`) so Boot 4 doesn't add a second mapper. `@SafeQuery` is deprecated → `@SafeUrl`. Jackson 3 = `tools.jackson.*`.
**Maven:** `org.opentmf.commons:opentmf-commons` (BOM-managed).

### opentmf-json-patch
**What:** Jackson 3-native RFC 6902 (JSON Patch) + RFC 7396 (JSON Merge Patch) — replaces the Jackson-2-bound `com.github.fge:json-patch`.
**Use it for:** Building/parsing/applying patch bodies in Boot 4 / Jackson 3 code (e.g. api-clients `patch(...)`).
**Key API:** `JsonPatch.builder().add/remove/replace/move/copy/test(...).build()`, `fromJson`, `apply(JsonNode)` (returns new node); `JsonMergePatch.fromJson/apply`; `JsonPatchException`.
**Config:** none.
**Snippet:**
```java
JsonPatch p = JsonPatch.builder().replace("/lifecycleStatus", "Retired").build();
JsonNode out = p.apply(doc);   // atomic; original untouched
```
**Gotchas:** Application is atomic — any failing op throws and leaves the original unchanged. Merge-patch replaces arrays wholesale; a `null` field means remove. Jackson 3 only; package `org.opentmf.commons.patch`.
**Maven:** `org.opentmf.commons:opentmf-json-patch` (BOM-managed).

### opentmf-errors
**What:** Framework-agnostic error-code registry (`ErrorCode` contract + 59-entry `CommonErrorCode` seed catalog, wire-identical to the dnext "Back End Module Error Codes") with optional Spring renderers.
**Use it for:** Emitting stable, machine-readable error codes on the wire — as an RFC 9457 `ProblemDetail` or a TMF-style `Error` body — instead of string-building codes in business code.
**Key API:** core — `ErrorCode` (`code()`, `httpStatus()`, `reasonTemplate()`, `remedy()`, default `reason(Object...)` / `reason(Map<String,?>)`), `CommonErrorCode` enum (+ `findByCode(String)`), `ErrorTemplate.format(template, args)`; resources `org/opentmf/errors/error-codes.json` and `org/opentmf/errors/opentmf-errors-oas31.yaml` (`#/components/schemas/Error`, `#/components/schemas/ProblemDetail`). spring — `ProblemDetailRenderer.render(code, reasonArgs…)` / `renderWithDetail(code, detail, reasonArgs…)` (+ `TYPE_PREFIX`), `TmfErrorRenderer.render(code, reasonArgs…)` (+ `TYPE`), DTO `TmfError` (`code`, `reason`, `message`, `status`, `referenceError`, `errorDetail`, `@baseType`/`@schemaLocation`/`@type`).
**Config:** none — no properties, no beans, no autoconfig; renderers are static.
**Snippet:**
```java
ProblemDetail p = ProblemDetailRenderer.renderWithDetail(CommonErrorCode.NOT_FOUND, "No customer with id 42");
TmfError e = TmfErrorRenderer.render(CommonErrorCode.BUSINESS_VALIDATION, "BVR_042", "quota exceeded");
```
**Gotchas:** `opentmf-errors-core` is zero-dep (test-scope Jackson only); `opentmf-errors-spring` pulls `spring-web` + `jackson-annotations` only — no Boot autoconfiguration, you own the single `@RestControllerAdvice` mapping exceptions→`ErrorCode` (sample: `SampleGlobalExceptionMapper` in the spring test tree). Catalog is **append-only**: a published code never changes meaning or HTTP status, corrections mint a new variant. Code format is `NNN.NNN-VV` but `httpStatus()` is authoritative, not the leading segment — `500.522-98/-99` serve HTTP 400 and `200.200-99` (`DRY_RUN_SUCCESS`) is a success code in the error catalog. `ProblemDetail.type` is the dnext-generic URN `urn:dnext:error:<code>`; `TmfError` puts the same single code value on both `code` and `status`.
**Maven:** `org.opentmf.errors:opentmf-errors-core` + optional `org.opentmf.errors:opentmf-errors-spring` (BOM-managed since opentmf-versions 2.1.14, currently 1.0.0).

## TMF v4 models, API & utils

### opentmf-v4-api
**What:** Getter-only Java interfaces (`I*`, e.g. `IServiceOrder`) generated from TM Forum v4 OpenAPI specs — the contract layer, zero external deps.
**Use it for:** Depending on a lightweight TMF type contract (shared utils/clients) without pulling concrete models.
**Key API:** Interfaces only, per TMF (`org.opentmf.tmf641.model.IServiceOrder`, …). No beans/annotations/runtime behavior.
**Config:** none.
**Snippet:** `List<? extends IServiceOrderErrorMessage> errs = order.getErrorMessages();`
**Gotchas:** These are **getter-only model interfaces**, not Spring MVC controllers (the BOM README mislabels them). Depend on the specific per-TMF module(s) you need.
**Maven:** `org.opentmf.model:opentmf-{NNN|group}-v4-api` (BOM-managed).

### opentmf-v4-models
**What:** Concrete TM Forum v4 DTO classes (Lombok + Jackson polymorphism + validation), each implementing the matching `I*` interface.
**Use it for:** The actual request/response DTOs in a TMF service (e.g. `ServiceOrder`, `CancelServiceOrder`).
**Key API:** Model classes (`org.opentmf.tmf641.model.ServiceOrder`, …) + one `Tmf<NNN>JacksonConfig.registerExtensions(JsonMapper.Builder)` per module that registers its polymorphic subtypes.
**Config:** none — wire a `JsonMapper` bean and call `registerExtensions` yourself.
**Snippet:**
```java
@Bean @Primary JsonMapper jsonMapper() {
  var b = JacksonUtil.defaultMapperBuilder();
  Tmf641JacksonConfig.registerExtensions(b);     // TMF-641 + Service subtypes
  var m = b.build(); JacksonUtil.setDefaultJsonMapper(m); return m;
}
```
**Gotchas:** Polymorphic deserialization fails unless you call `registerExtensions` for **each** TMF module you use directly — subtypes aren't auto-registered.
**Maven:** `org.opentmf.model:opentmf-{NNN|group}-v4-model` (BOM-managed).

### dnext-v4-models
**What:** Concrete TMF v4 POJOs in the DNext flavor (`org.opentmf.dnext.tmfNNN.model.*`), each implementing the `opentmf-v4-api` `I*` interface.
**Use it for:** Typed DTOs for a DNext-integrated service; depend on the specific `dnext-NNN-v4-model` module(s) used.
**Key API:** Model classes (`org.opentmf.dnext.tmf622.model.ProductOrder`, …); `TmfNNNJacksonConfig.registerExtensions(JsonMapper.Builder)` for subtype registration.
**Config:** none.
**Snippet:** `var b = JacksonUtil.defaultMapperBuilder(); Tmf622JacksonConfig.registerExtensions(b);`
**Gotchas:** Maven **groupId is `org.opentmf.model`** (not `…dnext`) despite the `org.opentmf.dnext.*` package. Same per-module `registerExtensions` requirement as opentmf-v4-models.
**Maven:** `org.opentmf.model:dnext-NNN-v4-model` (BOM-managed).

### opentmf-v4-utils
**What:** Stateless helpers for any TMF v4 model implementing the `opentmf-v4-api` interfaces (characteristics, related parties, notes, product/service orders).
**Use it for:** Looking up/typing characteristics by name, finding related parties by role, reading TMF-622/641 fields without boilerplate.
**Key API:** `CharacteristicUtil` (`findCharacteristicByName`, `getMandatoryCharacteristicStringValue/BooleanValue/…`, `getOptionalCharacteristic*Value`, `toNameStringMap`); `RelatedPartyUtil` (`findRelatedPartyByRole`, `findCustomerParty`, …); `NoteUtil`; `ProductOrderUtil` (622), `ServiceOrderUtil` (641).
**Config:** none.
**Snippet:** `String imei = CharacteristicUtil.getMandatoryCharacteristicStringValue(p.getCharacteristic(), "IMEI");`
**Gotchas:** Pick the right module per scope: `opentmf-common-v4-util` / `opentmf-622-v4-util` / `opentmf-641-v4-util`. Your model must implement the `opentmf-v4-api` interfaces.
**Maven:** `org.opentmf.util:opentmf-{common|622|641}-v4-util` (BOM-managed).

## Outbound HTTP

### opentmf-api-clients
**What:** High-level TMF API client layer over opentmf-http-clients — one generic client bean per configured endpoint (CRUD + JSON/merge patch + pagination), no per-API code.
**Use it for:** Calling another TMF service's resources by config alone, instead of hand-rolling URLs over a raw RestClient.
**Key API:** Bean `GenericTmfClient` (sync; `-rest`) / `GenericReactiveTmfClient` (`-reactive`); typed clients via `TmfClientFactory.create(serverConfig, "endpoint", R.class)`; pub/sub `TmfHubClient`; pagination `TmfOffsetRequest`/`TmfPage`; errors `OpenTmfClientResponseException`/`OpenTmfClientNotFoundException`. Since **3.0.0: ENTITY VIEW** — `client.entity()` returns a `TmfEntityClient` (sync) / `ReactiveTmfEntityClient` (reactive) whose verbs answer `ResponseEntity<...>` / `Mono<ResponseEntity<...>>`, so the status code and response headers (`Location` after a create, `ETag` for a conditional follow-up, custom `X-*`) are readable on the **success** path; same eight verb families and 8-overload ladder as the body view, and `sub(...)` composes (`client.sub(...).entity()`). Since 2.1.0: **`sub(template, vars...)`** on both `TmfClient` and `ReactiveTmfClient` returns a derived client scoped to a nested path, so every verb (get/list/listAll/listPaged/post/put/patch/delete) works against it unchanged and at arbitrary depth — e.g. `orderClient.sub("/{orderId}/action/{action}/item", orderId, action).get(itemId, Item.class)` issues `GET /order/{orderId}/action/{action}/item/{itemId}`; vars bind as URI template variables and are strictly encoded (a value containing `/`, `:` or `{` cannot inject), and template/argument arity is validated before any request is issued. **Bean name = `<server>.<endpoint>TmfClient`** (relaxed-bound keys, e.g. qualifier `catalogManagement.productOfferingTmfClient`).
**Config:** prefix `opentmf.api-clients.<server>.*`: `client-ref` (→ an `opentmf.http-clients` entry), `base-url`, `context-path` (default `""`), `fixed-headers`, `endpoints.<name>.{path, fixed-headers, scopes}`. Autoconfig `TmfApiClientsAutoConfiguration`.
**Snippet:**
```java
@Qualifier("catalogManagement.productOfferingTmfClient") GenericTmfClient client;
ProductOffering po = client.get("123", ProductOffering.class);
```
**Gotchas:** Unlike the raw http-clients `RestClient`, `GenericTmfClient` **auto-attaches** the bearer token (via `HeaderUtil` + the `<clientRef>TokenService`) and validates it's present — so reach for api-clients (not a hand-used `RestClient`) whenever you're calling a TMF resource and want auth handled. Endpoints whose path ends `/hub` get only a `TmfHubClient`, no generic bean. REST and reactive are separate modules — don't pull WebFlux into a servlet app. Endpoint `fixed-headers` override server-level on collision. Since 2.1.0, direct callers of `UriBuilderUtil.buildUriWithId(server, endpoint, id, null)` passing a **null literal** must cast it to `(TmfRequestContext) null` — the new `SubResourcePath` overload makes the call ambiguous otherwise; binary compatibility and the typed clients' API are unaffected. ⚠ **3.0.0 upgrade:** reactive `listPaged*` now returns `Mono<TmfPage<List<R>>>`, not `Mono<TmfPage<Flux<R>>>` — the old body `Flux` was a single-subscription live connection stream, so reading only the page metadata left the connection undrained and the content could never be read twice. Migrate `flatMapMany(TmfPage::getContent)` → `flatMapIterable(TmfPage::getContent)` (the repo ships a MIGRATION.md). Reactive `list`/`listAll` keep their `Flux<R>` signatures but now buffer each page before emitting its items. **`AuthType.NONE` finally works** — such a client used to throw `IllegalArgumentException: Authorization token must not be empty.` on every call before anything reached the network, and now sends no `Authorization` header at all; a token passed to a `…WithToken` overload on a NONE client goes out verbatim as the whole credential, so include the scheme yourself (`"Bearer eyJ…"`). Mirror-image change for authenticated clients: a BEARER/BASIC client whose token service returns a **blank** token now fails locally instead of sending `Authorization: Bearer ` and collecting a remote 401 — the guard was always documented but never actually fired. No entity form exists for `listAll*` (N pages means N header sets) or `listPaged*` (`TmfPage` already *is* the header-derived view). Errors still throw `OpenTmfClientResponseException`, whose headers remain the source for a failed response. Extension point moved: `HeaderUtil.headersConsumer(...)` takes a fifth `AuthType` argument and owns the whole authorization decision, `validateAuthorization` is gone, and no four-argument overload was kept — every call site must state its auth type. ⚠ **3.1.0 upgrade: nothing is retried automatically any more.** Up to 3.0.0 every verb of `TmfClient`/`ReactiveTmfClient`/`TmfHubClient`/`ReactiveTmfHubClient` was silently retried (default 3 times, 5 s doubling backoff) on 408/429/500/502–504/509 — including non-idempotent `POST`s, which could duplicate a create. Every request is now sent exactly once; `num-retries` / `retry-wait-duration` drive bearer-token retrieval only, as the http-clients contract always said. No signature or config change. A caller that relied on the implicit retry (typically a `GET`) wraps it itself: `SyncClientUtil.executeWithRetry(...)` (sync) or `.retryWhen(WebClientUtil.retry(...))` (reactive) — see the repo's MIGRATION.md "From 3.0 to 3.1".
**Maven:** `org.opentmf.client:opentmf-api-clients-rest` (or `-reactive`/`-hub`/`-common`) (BOM-managed).

### opentmf-http-clients
**What:** Spring Boot HTTP client factory — builds configured `RestClient`/`RestTemplate`/`WebClient` beans per YAML entry, with OAuth2 bearer/basic auth, Caffeine token caching, mTLS, fixed headers, Logbook wiring.
**Use it for:** The transport under api-clients, or any standalone outbound client needing token auth from config. `client-ref` points here.
**Key API:** Per-`<id>` beans `<id>RestClient`, `<id>RestTemplate`, `<id>WebClient`, `<id>TokenService`. Utils `SyncClientUtil` (`executeWithRetry`, `emptyOn404`), `WebClientUtil`, `HttpClientUtil`. Ordering marker bean `opentmfHttpClientsStarter` (`@DependsOn`). Since **2.5.1: A TOKEN ANSWER WITHOUT A USABLE TOKEN FAILS BY NAME** — on both token paths (`SyncTokenClientImpl`, `BearerTokenClientImpl`) a success answer with an empty body, a non-JSON-object body, or a missing / non-string / blank `bearer-auth.token-field` throws **`BearerTokenResponseException`** (`org.opentmf.client.bearer.exception`, an `OpenTmfClientResponseException`: `tokenUrl`, `tokenField`, `reason` = `EMPTY_BODY`/`NOT_A_JSON_OBJECT`/`FIELD_MISSING`/`FIELD_NOT_A_STRING`/`FIELD_BLANK`); the message names the endpoint, status and field, never the body; not retried, nothing cached. `BearerTokenUtil.readTokenResponse` is the shared check for hand-minted tokens. Since **2.5.0: THE TOKEN CALL IS ITS OWN** — a client's `fixed-headers` no longer reach its bearer-token endpoint (on every client type and for `HttpClientRegistry` clients); the token call carries only its protocol headers (`Content-Type`, Basic `Authorization` when client-id/secret are set, `Accept` on `netty`) plus the new `bearer-auth.headers`. The sync token call still shares the pool, the `OutboundInterceptorContribution`s, resilience and Logbook. Reactive clients are each built from their own clone of the `WebClient.Builder` (`WebClientConfigUtil.createTokenWebClient` / `ReactiveClientRegistrar.createTokenWebClient` build the token `WebClient` without fixed headers); the sync fixed-headers interceptor is the named `FixedHeadersClientHttpRequestInterceptor`. Since **2.4.0: ONE INTERCEPTOR ON EVERY CLIENT** — an `OutboundInterceptorContribution` bean (`opentmf-http-clients-rest`; a `ClientHttpRequestInterceptor` + order, one-arg constructor = `LOWEST_PRECEDENCE`, `@Order` on the `@Bean` method wins) runs first, ahead of resilience → gzip → fixed headers → Logbook, on every `<id>RestTemplate`/`<id>RestClient`, every `<id>TokenService` token call and every sync `HttpClientRegistry` client. Throwing refuses the call before the wire, the exception reaches the caller unchanged and the circuit breaker does not count it. `WebClient` (netty) clients and self-built clients are not covered. Since **2.2.0: TOKEN-MINT RETRY + OBSERVABILITY** — a bearer token mint (sync and reactive) is retried exactly once, immediately, on a transport-level failure (stale keep-alive, reset, premature EOF, I/O timeout at headers or body stage), never on a status error or an open circuit breaker; a mint that still fails throws **`BearerTokenTransportException`** (`org.opentmf.client.bearer.exception`: `tokenUrl`, `attempts`, cause) instead of the raw `ResourceAccessException`/reactor error — not a response exception, so the retry utilities never retry it (map it to 503). One `INFO` per successful mint (issuer URL, scope, attempt, duration) and, with a `MeterRegistry`, counter `opentmf.client.token.fetch{client, outcome=ok|retried|failed}` (Prometheus `opentmf_client_token_fetch_total`); `TokenFetchListener` (`org.opentmf.client.bearer.observe`) / `TokenFetchMeters` bean for hand-wired token clients; `RestClientRegistrar.createTokenService(clientId, RestClient, ClientProperties)` overload. Since **2.1.7: TRACE PROPAGATION** — every library-built client (JDK and Apache `RestTemplate`, the derived `RestClient`, the reactive `WebClient`; static, dynamic and token clients alike) is wired to the application's Micrometer `ObservationRegistry` bean when one exists, so with Micrometer tracing every outbound request carries `traceparent` and the trace continues across the hop; without a registry or a tracer nothing changes, and no dependency is added. Since 2.1.4: **`HttpClientRegistry`** bean for runtime/programmatic clients (`getOrCreate(name, ClientType, props)` / `replace` / `evict`, reactive `getOrCreateReactive`; handle exposes `restClient()`/`webClient()`/`tokenService()`); **`ClientPropertiesValidator.validate(ClientType, props)`** — static, side-effect-free, returns ALL findings at once (SRE "test connection" checklists); **`OpenTmfClientResilienceException`** for circuit-open/bulkhead-full rejections (deliberately OUTSIDE the `OpenTmfClientResponseException` hierarchy so retry utils never retry it; map to 503).
**Config:** prefix `opentmf.http-clients.<id>.*`; global `opentmf.client-type` (default `jdk`; `apache`/`netty`). Per-client `base-url`, timeouts, `num-retries` (3); auth block `bearer-auth.{token-url, client-id, client-secret, form-data:{grant_type,…}, headers:{name: value}}` (`headers` since 2.5.0: sent on the token call only; cannot replace its `Content-Type` or its Basic `Authorization`) or `basic-auth.{username,password}` (block presence selects auth; neither = no-auth). Since 2.1.4: optional **resilience4j** per client under `<id>.resilience.*` — `enabled` (false), `circuit-breaker.{failure-rate-threshold=50, slow-call-rate-threshold=100, slow-call-duration-threshold=5s, sliding-window-size=50, minimum-number-of-calls=20, wait-duration-in-open-state=30s, permitted-calls-in-half-open=5, record-status-codes=[500,502,503,504]}`, `bulkhead.{max-concurrent-calls=0, max-wait-duration=0s}`, `time-limiter.timeout-duration` (reactive-only). Property javadoc now ships as IDE `spring-configuration-metadata`. Autoconfig `OpentmfHttpClientsAutoConfiguration`.
**Snippet:**
```java
@Qualifier("dsyncRestClient") RestClient client;
Optional<Catalog> c = SyncClientUtil.emptyOn404(() -> client.get().uri("/catalog/123").retrieve().body(Catalog.class));
```
**Gotchas:** ⚠ **2.2.0 upgrade:** code that caught `ResourceAccessException` / `RestClientException` around a token mint now sees `BearerTokenTransportException` (status errors unchanged); the sync token client did not retry retryable statuses per `num-retries` before 2.3.0 (only the reactive one did). ⚠ **2.3.0 upgrade:** library-built **sync** token clients now retry a `503`/`429`/… from the token endpoint per `num-retries` (default 3) / `retry-wait-duration` / `max-retry-after` — a sync mint that used to fail fast on the first `503` now waits through the retries; set `num-retries: 0` to keep the old behaviour; hand-wired clients opt in with the new `SyncTokenClientImpl(RestClient, ClientProperties, BearerAuthConfig, TokenFetchListener)` constructor. The transport-retry `WARN` and `BearerTokenTransportException` message now carry the whole cause chain (`TransportFailures.describeChain`), so log alerts matching the old text may need updating. ⚠ **Before 2.2.1** a servlet-only service with `spring-webflux` on the classpath transitively (e.g. Spring AI Ollama) failed at startup with `NoClassDefFoundError` from `ReactiveClientRegistrar`; 2.2.1 conditions each registrar on its own module's class. The `<id>RestClient` / `<id>WebClient` are the raw transport — neither attaches a bearer token on its own (their only auto-headers are fixed-headers, `Accept`, gzip, Logbook). This is deliberate: attaching auth is the caller's job so a client can forward an existing/customer token (relay / on-behalf-of) instead of always minting a service token. Inject the `<id>TokenService` (sync) / `TokenService` (reactive) bean and stamp `Authorization: <getTokenType()> <getToken()>` yourself (e.g. a `requestInterceptor` via `restClient.mutate()` — which copies the interceptor list, leaving the exposed bean untouched). Only **opentmf-api-clients** (`GenericTmfClient`) attaches the token for you — so a raw client consumer that assumes auto-auth will send unauthenticated requests and get 401s. Beans are registered programmatically → IDEs flag false "cannot autowire"; add `@DependsOn("opentmfHttpClientsStarter")` if a `NoSuchBeanDefinitionException` hits at startup. Does NOT auto-retry calls (opt-in via the utils); only token retrieval retries. ⚠ **Since 2.1.6 this is finally TRUE for Apache too** — `client-type: apache` previously inherited Apache's `DefaultHttpRequestRetryStrategy`, silently retrying 429/503 once even with retries off, and STACKING on caller retries (`num-retries: 3` → up to 8 attempts on Apache vs 4 on JDK/Netty). Removed in 2.1.6: one owner, opted into at the call site via `executeWithRetry`/`WebClientUtil.retry`, all three backends identical. **If you were on `apache` and relying on the implicit retry, you now get none — opt in explicitly.** ⚠ **2.1.7 upgrade:** where the `ObservationRegistry` carries metrics handlers (Spring Boot Actuator), outbound calls now also record the standard `http.client.requests` observation — new metric series on dashboards, with their cardinality. Logbook is optional and not transitive — add `logbook-spring-boot-autoconfigure` or wire-logging silently no-ops (since 2.1.2 a present starter is picked up via `ObjectProvider`, no spurious warning). Since 2.1.3 `fixed-headers` are **defaults, not overrides** on the REST side — a per-request header wins (also fixes token retrieval when `fixed-headers.Content-Type` is set). Resilience is off by default AND classpath-gated (consumer adds the resilience4j jars); one config decorates every client shape of the id INCLUDING its bearer-token calls (a broken IdP opens the same circuit); order bulkhead → breaker → time limiter, with `executeWithRetry` OUTSIDE; 4xx never trips the breaker (`emptyOn404` unaffected). Per-type semantics: `request-timeout` = connect timeout on JDK/Netty but pool-lease timeout on Apache; `max-connections`/`connection-idle-timeout` are IGNORED by the JDK client (validator flags it — use `apache` or the bulkhead). Apache clients + a `MeterRegistry` expose pool gauges `opentmf.client.pool.{leased,available,pending,max}{client=<name>}`. Registry-retired clients close after a 30s grace (JDK close is real only on Java 21+ runtimes); `replace`/`evict` reset that name's resilience instances; prefer `client-type: apache` for dynamic sources. ⚠ **2.4.0 upgrade:** nothing changes without an `OutboundInterceptorContribution` bean. A contribution applies to EVERY covered client, so one meant for some clients only must decide from `request.getURI()` itself. It sees the request before fixed headers are filled, so a header it sets overrides a `fixed-headers` default. Declare it in a configuration class that does not inject the library's client beans, or you get a circular dependency (contributions are looked up when each client is built, at startup or registry registration). `JdkRestTemplateFactory`/`ApacheRestTemplateFactory` gained an `ObjectProvider<OutboundInterceptorContribution>` constructor argument, which breaks only code that constructs them by hand. ⚠ **2.5.0 upgrade:** a client whose identity provider needs one of its `fixed-headers` (e.g. a gateway `x-api-key` the IdP also checks) must repeat it under `bearer-auth.headers`, or its token mint now fails — before 2.5.0 every fixed header went to the token endpoint too (since 2.0.0). ⚠ **2.5.1 upgrade:** a token answer without a usable token now throws `BearerTokenResponseException` (before: a bare `NullPointerException`, a parser error quoting the body, an empty reactive `getToken()`, or a blank token used as one). Its `getStatusCode()` is the **success** status the endpoint sent, so a handler mapping `OpenTmfClientResponseException` by status sees a 2xx — map it on its type. ⚠ **Before 2.5.0** reactive clients leaked into each other through one shared `WebClient.Builder`: each carried the fixed headers, base URL and error filter of every client built before it, and a client without a `base-url` resolved relative URIs against an earlier client's.
**Maven:** `org.opentmf.client:opentmf-http-clients-starter-rest` (or `-starter-reactive`/`-starter`, `<type>pom</type>`) (BOM-managed).

## Query, security, audit, locking

### tmf630-toolkit
**What:** Server-side Spring MVC library turning TMF-630 query params into QueryDSL `Predicate`s, plus paging/sorting/field-selection response helpers.
**Use it for:** Any read endpoint that accepts `field.op=value` filters, signed `sort`, `offset`/`limit`, `fields=` projection, or a JsonPath `filter=`.
**Key API:** `@QuerydslPredicate(root = Entity.class) Predicate` param (repo extends `QuerydslPredicateExecutor`); `@Tmf630Response` for status + `Content-Range`/`X-Total-Count` headers + field selection; `Tmf630Util.tmfPage(Page)`; enum `TmfOperator`. Since **3.5.1: LISTS REFUSE SPRING'S `page`/`size`** — under `WARN`/`REJECT` a TMF-630 list is judged for the two names the filter parser skips: bare `page`/`size` are reported or refused (`TmfUndeclaredQueryParameterException.isListRoute()`, message `… is a TMF-630 list, which pages with offset and limit`), unless the handler binds the name itself. `page.eq=`/`size.eq=` stay filters, and `Tmf630DeclaredQueryParameters.listRefusals(HandlerMethod)` exposes the set. Since **3.5.0: UNDECLARED QUERY-PARAMETER GUARD (opt-in)** — `Tmf630UndeclaredQueryParameterInterceptor` judges `GET`/`HEAD` handler methods against the names their signature declares (`@RequestParam`s; `offset`/`limit`/`sort` for a `Pageable`; `sort` for a `Sort`; `version` for a `TmfVersionedId`; `fields` where `@Tmf630Response` runs; `@Tmf630PassThrough` names). TMF-630 filter lists and handlers it cannot see into (`@RequestParam Map`, raw request, model attribute) stay open. `@Tmf630AcceptsQueryParameters({...})` names a handler's vocabulary, and `@Tmf630AcceptsAnyQueryParameter` exempts one (e.g. a gateway callback). The refusal is `TmfUndeclaredQueryParameterException` (a `ServletRequestBindingException`, message `unknown query parameter 'x' — GET /route takes only a, b`), rendered by `Tmf630UndeclaredQueryParameterExceptionHandler` as `"reason": "Unknown query parameter."`. `Tmf630UndeclaredQueryParameterListener` beans see every warned or refused request, and `Tmf630QueryArgumentClassifier` says what an app-resolved argument reads. Contract tests use `Tmf630DeclaredQueryParameters.of(HandlerMethod)` → `Optional<Set<String>>` (empty = open) and `Tmf630QueryParameterContract`, which diffs every judged GET route against its OAS operation's `in: query` parameters and lists open routes. Since **3.4.0: REGEX ON JPA = LIKE SUBSET** — with `regex.enabled=true`, `.regex`/`.regexi`/Part 6 `=~` on an `@Entity` root render literals, `\`-escapes, `.`, `.*`, `.*?`, edge `^`/`$` and the `i` flag as `like`/`lower(…) like lower(…)` (unanchored = contains), same rows as Mongo/JSONB; anything else is a 400 naming the subset. JSONB `filter=` `=~` lowers to `like_regex`. Since **3.3.0: BOUNDED `Link` HEADER + QUERY-PARAMETER GUARD** — the paging `Link` header is **omitted** when any single query-parameter value exceeds `paging.link.max-param-value-length` (256) or the assembled header would exceed `paging.link.max-length` (2048); `X-Total-Count`/`X-Result-Count`/`Content-Range` and the status are unchanged (new `Tmf630LinkHeaderSettings` record + `Tmf630Util.applyLinkHeader(...)` overload). `Tmf630QueryLimitsInterceptor` (on every mapping, via `Tmf630QueryLimitsAutoConfiguration`) rejects a single value longer than `query-limits.max-param-value-length` (2048) with **400** and a query string longer than `query-limits.max-query-string-length` (4096) with **414**, both as TMF `ErrorMessage`; `Tmf630HeadersTooLargeRecoveryResolver` answers Tomcat's `HeadersTooLargeException` once with a chunked 500 TMF body instead of an empty `500` + `Connection: close`. Since **3.2.0: PASS-THROUGH PARAMETERS** — `@Tmf630PassThrough({"version"})` on the handler (or its API-interface method) exempts exact-named non-entity query parameters from both filter terminals (`@QuerydslPredicate`, `@Tmf630JsonbFilter`) under `on-unknown-field=REJECT`; exact names only (`version.eq` is still a filter key), nothing global. Since **3.1.0: JSONB URL BINDING** — `@Tmf630JsonbFilter(root = X.class) JsonbClause` on a `@Tmf630JsonbBacked` endpoint binds the full TMF-630 URL grammar, as `@QuerydslPredicate` does for QueryDSL (dot-suffix operators, encoded operator literals, comma/semicolon OR lists, allowlists, clause/value limits, `filter=` JsonPath, `filter.combineWithAttributes`) — no hand-parsed filter params. Both terminals share the backend-neutral `Tmf630FilterParser`, and `Tmf630FilterSettings` is now an application bean (`@ConditionalOnMissingBean`), so `attribute-filtering.*` settings reach the JSONB backend too. Since 3.0.0 (major), optional modules: `tmf630-toolkit-jpa-correlated-sort` (`Tmf630JpaCorrelatedSortExecutor` — dotted/`[k=v]`-correlated/multi-hop sorts, `min()`/`max()` wrappers, auto-wired on an `EntityManager`), `tmf630-toolkit-jsonb` (Postgres `payload jsonb` backend: `@Tmf630JsonbBacked`, filter/write executors, sub-resource controller — the escape hatch for everything JPA rejects), `tmf630-toolkit-mongo-split-collection` (`@Tmf630MongoSplitBacked`, split-aware translators); plus TMF-630 Part-4 **entity versioning**: `TmfVersionedId` path binding (`/X:(version=1.0)`), `@Tmf630Versioned(versionOrder = LEX|NUMERIC_STRING|SEMVER)`, `Tmf630VersionResolver` (JPA/Mongo/Jsonb impls).
**Operator suffixes (exact):** `eq, ne, eqi, nei, gt, gte, lt, lte, between, in, nin, isnull, isnotnull, like, likei, contains, containsi, startswith, startswithi, endswith, endswithi, regex, regexi`. (`*i` = case-insensitive; `in/nin/between` multi-value; `isnull/isnotnull` valueless.) Sort: `-field` = descending.
**Config:** `opentmf.tmf630.paging.*` (`default-limit=50`, `max-limit=500`, `strict-mode=true`, `link.max-param-value-length=256`, `link.max-length=2048`); `opentmf.tmf630.query-limits.*` (`enabled=true`, `max-param-value-length=2048`, `max-query-string-length=4096` — independent of `paging.enabled`); `…field-selection.default-depth=1`; `…attribute-filtering.*` (`implicit-eq-enabled=true`, `on-unknown-field=REJECT`, `regex.enabled=false`, `json-path-filter.enabled=true`, since 3.1.0 `allow-nested-paths-docdb=true` — the policy for nested paths on JSONB endpoints); since **3.5.0** `opentmf.tmf630.undeclared-query-params.*` (`on-undeclared=IGNORE` / `WARN` / `REJECT`, `exception-handler.enabled=true`, `non-query-arguments` = types or annotations of app-resolved arguments that read no query name). Autoconfigs `Tmf630WebMvcConfigurer`, `Tmf630AttributeFilteringAutoConfiguration`, `Tmf630FieldSelectionAutoConfiguration`.
**Snippet:**
```java
@GetMapping("/persons") @Tmf630Response
Page<Person> list(@QuerydslPredicate(root = Person.class) Predicate p, Pageable pageable) {
  return repo.findAll(p, pageable);
} // GET /persons?surname.startswith=D&born.gte=1990&sort=-surname&limit=20&fields=id,surname
```
**Gotchas:** ⚠ **3.3.0 upgrade — `Link` is now optional on the wire:** any client that pages by following `Link: rel="next"` must fall back to `offset`/`limit` against `X-Total-Count` when the header is absent (it is omitted, never truncated, over the budget — TMF-630 Part 1 §4.5.1 makes it a SHOULD). A request carrying a query-parameter value > 2048 chars now answers 400 and a query string > 4096 chars answers 414 before any handler runs (`query-limits.enabled=false` switches the guard off); before 3.3.0 the same request on a paged endpoint was an empty `500` + `Connection: close`, because the `Link` header echoed the full query string four times past Tomcat's 8 KB header buffer. Use `tmf630-toolkit-all` to get both filtering autoconfigs. Unknown field/operator → 400 by default (`on-unknown-field=REJECT`). `default-depth=1`: `fields=address` expands only scalar sub-fields — use a dot-path or raise depth for associations. **3.0.0 breaking:** `.regex`/`.regexi` (and JSONPath `=~`) on a JPA `@Entity` now 400 at parse time instead of silently degrading to SQL `LIKE`; deprecated escape hatch `opentmf.tmf630.attribute-filtering.regex.allow-jpa-like-semantics=true` restores old behavior with a one-time WARN (jsonb module supports real regex). ⚠ **3.4.0 upgrade:** nothing changes unless `regex.enabled=true` (default `false`; a test pinning `400 "Regex operator is disabled."` stays green). Once enabled, in-subset patterns on a JPA root answer **200** where 3.0.0 – 3.3.0 refused them — re-pin any test that pinned that refusal in the same change that enables the operator. `allow-jpa-like-semantics` is now **inert** (binds, logs one WARN asking for removal; gone in 4.0.0), and the `500` it produced for `^`/`[...]`/`\d` patterns is a 400; caller-typed `%`/`_` now match literally on JPA instead of acting as wildcards. New `opentmf.tmf630.paging.nulls-last=true` decorates sorts with `nullsLast()` (synthetic `CASE WHEN` cost on non-native dialects). Sub-resource base controllers now carry `@Tmf630Response` themselves — subclasses get headers/`fields=` without annotating. JPA `filter=` got stronger: array correlation via correlated `EXISTS` on JOIN-mapped collections, positional `[N]` via `INDEX(alias)` (requires `@OrderColumn`); JSON-column collections still 400. Versioning `LEX` order trap: `"1.10" < "1.9"` — use `NUMERIC_STRING`/`SEMVER` (which sort in-JVM, O(N) per logical id). Mongo: OR-of-splits needs `$unionWith` — illegal inside a multi-document transaction. **3.0.1:** `.regex`/`.regexi` and the LIKE family now accept polymorphic (`Object`/`Serializable`) value fields on the **Mongo and JSONB** backends (TMF-620-style `productSpecCharacteristicValue.value`) — no effect on plain JPA entities. ⚠ **3.1.0 upgrade:** the `tmf630-toolkit-jsonb` module runs on Jackson 3 (`tools.jackson`). Boot 4 needs nothing; a Boot 3 consumer must add `tools.jackson.core:jackson-databind` and declare a `JsonMapper` bean, or boot fails with `Tmf630JsonbConfigurationException` naming the missing bean. Payload (de)serialization failures throw `Tmf630JsonbSerializationException` instead of `UncheckedIOException` — move any catch block. `tmf630-toolkit-mongo-split-collection` no longer brings `jackson-databind` transitively. An invalid `filter.combineWithAttributes` value now always answers 400 (it was ignored when only one filter side produced a predicate). ⚠ **3.1.1 upgrade:** a plain-`Pageable` endpoint called without `offset`/`limit` now serves `paging.default-limit` (50) rows instead of Spring's hard-coded 20, and Spring-grammar `?size=` is capped at `paging.max-limit` (500) instead of Spring's 2000. ⚠ **3.2.0 upgrade:** on a handler that binds a filter root (`@QuerydslPredicate(root = X)` / `@Tmf630JsonbFilter(root = X)`), a plain `sort=` key must be a declared field of `X`, so **a correct `sort=` on a getter-only (derived) property that Spring Data accepted now answers 400** — no typo needed; unknown or mistyped keys 400 too (were a 500 on JPA, a silent 200 on Mongo/JSONB). Audit which sort keys clients send before rollout. Opt out with your own `TmfSortKeyValidator` bean (`TmfSortKeyValidator.NONE`). Handlers without a filter root, and correlated `[k=v]`/JsonPath sort terms, are unchanged. Take **3.2.1 or later** rather than 3.2.0: it removes regex backtracking a crafted JSONB `filter=` could use to burn request-thread CPU. ⚠ **3.5.0 upgrade:** the bump alone changes nothing (`on-undeclared=IGNORE` registers no interceptor and no handler). Switching a service to `REJECT` makes every `GET`/`HEAD` carrying a name its handler does not read answer **400**, and that includes Spring's `page`/`size` on a `Pageable` read, which only `offset`/`limit`/`sort` declare. Run `WARN` for one release first and read the `opentmf.tmf630.undeclared.query.params` counter by `uri` to find the callers. Under `REJECT`, `Tmf630QueryParameterContract` fails until the OAS declares `fields` on every `@Tmf630Response` read and `sort` on every `Pageable` read. A service that renders `ProblemDetail` sets `exception-handler.enabled: false`. A service with its own argument resolvers lists the non-query ones under `non-query-arguments`, or those handlers silently stay open (`openRoutes()` shows them). Replacing an in-house guard (dnms-journal's `@ForwardedQueryParameters`): there is no "always allowed" `offset`/`limit`/`fields`/`sort` any more — each name is accepted only where a handler reads it, so a catch-all's vocabulary must list `limit` itself. ⚠ **3.5.1 upgrade:** on `WARN`/`REJECT`, TMF-630 **lists** now report or `400` Spring's bare `page`/`size` too. Under 3.5.0 they passed unjudged: `?page=0&size=10` answered `200` with the default limit on a `TmfRichPageable` list, and Spring's page on a plain-`Pageable` one. List callers must page with `offset`/`limit`. A list that genuinely takes a `size` query parameter binds it on the handler. On `IGNORE` nothing changes.
**Maven:** `org.opentmf.query:tmf630-toolkit-all` (+ optional `tmf630-toolkit-{jpa-correlated-sort,jsonb,mongo-split-collection}`) (BOM-managed).

### openid-rbac-security
**What:** Spring Boot autoconfig for OAuth2 Resource Server (Bearer/JWT) RBAC with declarative, property-driven endpoint rules (servlet + reactive).
**Use it for:** Securing a service with JWT validation + per-method/path role rules expressed in config, not a hand-written `SecurityFilterChain`.
**Key API:** Fully autoconfigured — set properties only. Types `OpenTmfSecurityProperties`, `SecureEndpoint`, `OtherEndpoints` enum (`ALLOW`/`DENY`/`AUTHENTICATED`). Since **3.3.0: JWKS HEALTH + METERS** — opt-in `opentmf.security.jwks.readiness: true` registers a `jwks` health contributor (one component per issuer: `UP`; `UP`+`stale: true` while a cached set still serves through failed refreshes; `DOWN` exactly when that issuer's bearer requests answer 503) that joins the `readiness` group under Kubernetes probes, and a NotReady probe triggers one paced background JWKS retry; always-on per-issuer meters when Micrometer is present: `opentmf.security.jwks.keys`, `opentmf.security.jwks.keys.age` (s), `opentmf.security.jwks.fetch.failures`; the boot line names the JWKS host and route (proxy/direct), host only. Since **3.2.0: CACHE-FIRST SIGNING KEYS** (`org.opentmf.security.jwks`) — per-issuer JWK set loaded by a background warm-up at startup, refreshed ahead of expiry, served stale through outages, refreshed on an unknown `kid` at most twice per interval; no request thread ever fetches after the first load. An issuer whose keys were never obtained answers a typed **503** + `Retry-After` + problem type `urn:opentmf:security:problem:signing-keys-unavailable` (rendered through the app's own error rendering; `JwtService.decodeJwt` throws `JwkSetUnavailableException`). Proxy honour: `issuers[].proxy` / `jwks.proxy` → JVM proxy props → `HTTPS_PROXY`/`HTTP_PROXY` + `NO_PROXY` env → direct. `TrustedIssuerKeys` (from `JwksAutoConfiguration`) is now the second ctor arg of `ServletJwtSupport`/`ReactiveJwtSupport`; the `*ResourceRetriever` classes are gone. Since **3.1.0: THE HTTP-STATUS MATRIX** — one fixed order, evaluated by the library before anything else, on every path (whitelisted included) and both ports: **404** no handler for the path (anonymous or authenticated) → **405, no `Allow`** path exists but the method is not implemented on it, unknown method names (`PROPFIND`, `BREW`) included → **401** no/invalid token → **403** valid token, roles insufficient. The 404/405 bodies are the application's own error rendering — the library raises the exceptions Spring raises natively (`NoHandlerFoundException` / `HttpRequestMethodNotSupportedException`; `ResponseStatusException` / `MethodNotAllowedException` on reactive) through the application's resolvers, so a `@ControllerAdvice`, `ProblemDetail` or TMF-`Error` renderer answers them like everything else. "The path is served" counts every `HandlerMapping` in dispatcher order (functional routes, resource handlers, consumer mappings). Not configurable: `unmatched-method-response` is removed and setting it fails startup. Removed types: `UnmatchedMethodResponse`, `MethodNotAllowedAccessDeniedHandler`, `MethodNotAllowedServerAccessDeniedHandler`, `BlacklistDecision`, `ReactiveBlacklistDenial`; `EndpointRules.allowedFor` → `EndpointRules.answerFor`. New: `ServletHttpStatusMatrixFilter` / `ReactiveHttpStatusMatrixFilter`, `RetiredPropertyGuard`. Since **3.0.0: HTTP-METHOD SEMANTICS** — a `GET` rule also covers `HEAD`; plain `OPTIONS` on a served path answers 200 + `Allow`; rule `method` values are restricted to upper-case `GET`/`POST`/`PUT`/`PATCH`/`DELETE`. Since **2.3.0: MULTI-ISSUER** — `opentmf.security.issuers[]` (each entry: `name`, `issuer`, `jwk-set-uri`, optional `audiences`, optional claim overrides); tokens route to the entry matching their `iss`, and `JwtDecoder`/`ReactiveJwtDecoder` route by issuer so `JwtService` and out-of-filter decoding keep working. Since 2.2.0: **custom 401/403 bodies via optional consumer beans** — servlet `AuthenticationEntryPoint` (401) / `AccessDeniedHandler` (403), reactive `ServerAuthenticationEntryPoint` / `ServerAccessDeniedHandler`; bean presence is the switch (no new properties), each independent, applied to BOTH the bearer-token path and the exception-translation path; no bean → RFC 6750 defaults unchanged.
**Config:** prefix `opentmf.security`: `jwk-set-uri` (required), `user-claim` (default `sub`), `authorities-claim` (default `roles`), `secure-endpoints[]`, `whitelist[]` (any method), `blacklist[]`, `other-endpoints` (default `DENY`); `jwks.cache-ttl` (5m), `jwks.outage-ttl` (24h), `jwks.refresh-interval` (30s), `jwks.connect-timeout` / `jwks.read-timeout` (JVM defaults, then 30s), `jwks.on-startup-failure` (`warn` default: boot and serve 503 for that issuer until a refresh succeeds; `fail`: stop when NO issuer's keys loaded), `jwks.proxy` / `issuers[].proxy` (`host:port`), `jwks.readiness` (false — 3.3.0 health contributor + readiness-group membership; `management.health.jwks.enabled` also switches it off). Separate `opentmf.security.management.*` mirror for the management port (its `whitelist` defaults to actuator health/info; `other-endpoints` defaults `AUTHENTICATED`). Autoconfigs `ServletSecurityAutoConfiguration`, `ServletJwtAutoConfiguration` (+ reactive).
**Snippet:**
```yaml
opentmf.security:
  jwk-set-uri: http://idp/realms/r/protocol/openid-connect/certs
  whitelist: [/actuator/health, /v3/api-docs/**]
  secure-endpoints:
    - { method: POST, path: /orders/**, roles: [order-writer] }
```
**Gotchas:** ⚠ **3.2.0 upgrade — `HTTPS_PROXY` is now honoured for the JWK fetch:** a pod that exports `HTTPS_PROXY` without the identity provider's host in `NO_PROXY` fetched the keys DIRECTLY before (Java ignores the env) and goes through the proxy from 3.2.0 — the only deliberate change for a reachable issuer; set `NO_PROXY` or `issuers[].proxy`. With the default `on-startup-failure: warn` a service boots even when its issuer is unreachable and answers 503 for that issuer's bearer tokens until a refresh succeeds — health stays UP **unless you opt in to `jwks.readiness: true` (3.3.0)**, which makes the pod NotReady for exactly that case (and only that case: a stale-but-serving cache stays UP); without the opt-in, alert on the 503 problem type or the `opentmf_security_jwks_fetch_failures_total` meter. Remove any interim filter of your own that rendered 503 for this case, or two responders compete. 3.2.1/3.2.2 (servlet only): the 503's `Retry-After` is now on the wire exactly once whoever renders it — a mapper that rebuilds the `ResponseEntity` without headers, Spring's default resolver, or the bare fallback (3.2.0 lost it through app resolvers; 3.2.1 doubled it under the default resolver). ⚠ **3.1.0 upgrade:** a path with **no handler answers 404 to everyone, token or not** — the pre-3.1.0 non-disclosure answer (401 anonymous / 403 authenticated for a path outside the rules) is gone, so any contract test, WAF rule or probe that pinned 401/403 on an unknown path breaks; a path variable carrying a `/` that falls off the route table is now a 404, not a 403. The **405 carries no `Allow` header** and applies to unknown method names too (`PROPFIND`/`BREW` were a firewall 400 with Boot JSON; on a whitelisted path a servlet 501) — tests pinning `Allow`, or 401 for an anonymous unimplemented-method request, must be rewritten. **`unmatched-method-response` (3.0.0) now FAILS STARTUP if still set** (main or management section; `RetiredPropertyGuard` names it) — remove it before deploying. Blacklisted paths no longer answer a uniform 403: unmapped → 404, unimplemented method → 405, only an existing path+method reaches the rule. The error body is the application's own resolver output; without a `@ControllerAdvice`/`ProblemDetail` renderer the service gets Spring's default resolver → the container's error page, i.e. Boot's default error JSON in a Boot app (render `NoHandlerFoundException` / `HttpRequestMethodNotSupportedException` in your advice if you want your own body). Management port: an unexposed actuator path is 404 and an unserved method 405 — alerts keyed on 401/403 from that port need 404/405 added. A static-resource handler (Boot's `/**`) claims a path only when the resource resolves and implements `GET`/`HEAD` only; a request dispatched to a non-MVC servlet (H2 console, JAX-RS) bypasses the matrix; a consumer's own firewall bean takes precedence over the library's any-method-name firewall. `other-endpoints` (`DENY` on the main port, `AUTHENTICATED` on the management port — asymmetric on purpose) still governs **mapped** paths outside the rules only. Eval order: blacklist → whitelist → allowed-endpoints → secure-endpoints → other-endpoints. Management block applies only when `management.server.port` ≠ `server.port` — **and on servlet it actually works only from 2.2.0** (in 2.1.x Boot exposed the parent filter chain in the management child context, so main-port rules governed the management port; reactive was never affected). Unknown props fail fast. Custom 401/403 beans (2.2.0): apply to the MAIN port only; multiple candidate beans of one type → default kept + WARN naming candidates, disambiguate with `@Primary`; `@PreAuthorize` denials still reach `@RestControllerAdvice` as before. Behavior matrix surprises: a present-but-invalid token on a `permitAll` URL still → 401; an anonymous request on a `denyAll`/blacklisted URL → **401, not 403** (anonymous denials translate to authentication failures). Reactive trap: re-emitting the exception via `Mono.error` into Boot's `ErrorWebExceptionHandler` yields 500, not 401/403 — render the body in the bean (shared-renderer pattern) instead. **Multi-issuer (2.3.0):** configure EXACTLY ONE of `jwk-set-uri` or `issuers` — both, or neither, fails startup by design (as do duplicate `issuer`/`name` values). There is **no fallback issuer**: a token whose `iss` matches nothing, or that carries no `iss`, is 401 — deliberate. Single-issuer mode still does NOT check `iss`, so adding `issuers` is what turns issuer validation on. ⚠ **Set `audiences` when the provider mints tokens for many apps from one tenant (Entra especially)** — otherwise a token issued to a *different application of the same tenant* passes issuer validation. Entra field traps (README): tenant- and version-specific issuer values, prefer **App Roles** over group claims (which truncate), and `oid` is the stable principal while `preferred_username`/`upn` are readable but mutable. Entries inherit top-level `user-claim`/`fallback-user-claims`/`authorities-claim` unless they override — normalize onto ONE role vocabulary so `secure-endpoints` never forks per provider. ⚠ **3.0.0 upgrade:** the `GET`→`HEAD` coverage **tightens** as well as loosens — a `HEAD` probe used to fall through to `other-endpoints` (served anonymously under `allow`), and now carries the `GET` rule's roles, so a load balancer or uptime check `HEAD`ing a `secure-endpoints` path gets 401/403 unless it presents those roles or the path is whitelisted; the management section's `other-endpoints: authenticated` default makes this bite there by default. There is no opt-out. Delete every `method: HEAD` entry (a `GET` rule covers it; a duplicate `HEAD` rule never worked anyway — Spring Security applies the first registered match) and every `method: OPTIONS` entry (an `OPTIONS` rule cannot make a browser pre-flight succeed — that needs a `CorsConfigurationSource`); both now fail startup, as does a non-upper-case value like `get` (which was silently dead before, and relaxed binding would have brought it to life on upgrade). A method the code implements but the rules withhold is still `403` (never 405); a mapped path with an unimplemented method is 405 for anonymous callers too from 3.1.0 (3.0.0 answered 401 there, and 405 + `Allow` only once authenticated). Every `403` still reaches a consumer-supplied `AccessDeniedHandler`; only the plain-`OPTIONS` answer bypasses it.
**Maven:** `org.opentmf.security:openid-rbac-security` (BOM-managed).

### opentmf-db-lock-service
**What:** Cluster-level distributed lock over the app's own JDBC datasource (pure JDBC), with versioned upgrade/downgrade semantics and an auto-release safety timeout.
**Use it for:** Serializing once-per-cluster work (BPMN deployment, catalog sync, adapter version-gating), gated on a requested version.
**Key API:** `@UsingClusterLock(lockType=, requestedVersion=, downgradeAllowedAfter="PT10M", failureMessage=)` on a method; a `LockContext` method param the aspect enriches (`context.setSuccess(false)` to release without recording the version); `DbLockService.acquireLock(LockType, version)`; enum `LockType` (`BPMN`=B, `CATALOG`=C, `LOCK_X/Y/Z`); `DbLockException`. Since **3.0.0: ONE SHORT TRANSACTION PER STEP** — each acquire attempt, reclaim, release, `hasLock` and startup-sweep row runs in its own READ COMMITTED transaction on a connection borrowed for it alone and returned with its auto-commit and isolation restored, so a waiter no longer holds a pooled connection for its whole wait. The DDL runs as one transaction the library owns (it now persists under Hikari `auto-commit: false`). A lock's age and the `downgradeAllowedAfter` period are measured with the database's clock, and hold-timeouts share one daemon thread per instance. Helpers `JdbcHelper.inTransaction(JdbcTemplate, SqlWork)`, `JdbcHelper.getOffsetDateTime(ResultSet, String)`, `Dialect.getCurrentTimestampSql()`, `DialectDetector.fromConnection(Connection)`, `LatestLock.getReadAt()`. Since **2.2.2:** `LockVersionMigration` widens a legacy `lock_version VARCHAR(10)` once, through JDBC metadata, instead of an `ALTER` on every boot.
**Config:** prefix `opentmf.db-lock` (strict): `create-tables=true`, `lock-acquire-timeout=120000`, `lock-hold-timeout=300000`, per-type `duration-overrides`, `dialect` (auto-detected when unset), `ddl-location` (your own DDL script instead of the bundled one). Autoconfig `DbLockAutoConfiguration` (activates on `spring.datasource.url`). Tables `DB_LOCK`/`DB_LOCK_LATEST`/`DB_LOCK_HISTORY` (`lock_type CHAR(1)`).
**Snippet:**
```java
@UsingClusterLock(lockType = LockType.BPMN, requestedVersion = "1.3", failureMessage = "BPMN deploy failed")
void deploy(LockContext ctx) { /* runs once cluster-wide */ }
```
**Gotchas:** **NEVER pass `null` for the `LockContext` param — pass `new LockContext()`** so the aspect can enrich it. Tables are per-microservice (each service owns its own `db_lock_*`). A held lock auto-releases after `lock-hold-timeout`. Any thrown exception releases with `success=false`. DDL ships for Postgres/MySQL/MariaDB/Oracle/SQL Server/DB2/H2; dialect auto-detected. `lock-hold-timeout` is also everyone else's staleness threshold: work that outruns it loses the lock while still running. Do not run `@UsingClusterLock` inside a caller's transaction. On DB2 keep the JVM and the server in the same time zone (a plain `TIMESTAMP` is read as a JVM-zone `LocalDateTime`). ⚠ **3.0.0 upgrade:** `JdbcHelper.createTables(JdbcTemplate)` (deprecated since 2.2.0) is **removed** — call `createTables(JdbcTemplate, Dialect)` (`Dialect.POSTGRESQL` reproduces the removed overload) or `createTables(JdbcTemplate, Resource)` for a script of your own; no DNMS service calls it, and nothing else breaks binary compatibility. Behaviour you can see: on SQL Server/DB2 under `auto-commit: false` the tables are now actually created; instances starting together on an empty PostgreSQL schema all start; on every non-PostgreSQL dialect each recorded release after the first updates `DB_LOCK_LATEST` (before, work under `@UsingClusterLock` re-ran on every start); an interrupted waiter ends with `DbLockException`; `db/postgresql.sql` no longer carries its own `BEGIN`/`COMMIT` (matters only to a copied `ddl-location` template). ⚠ **Before 2.2.2** every PostgreSQL boot took an `ACCESS EXCLUSIVE` lock on the lock table, and several contexts booting on one database could fail with `PSQLException: deadlock detected`.
**Maven:** `org.opentmf.util:opentmf-db-lock-service` (BOM-managed).

### opentmf-outbox-service
**What:** Transactional outbox as a Spring Boot starter, over the app's own JDBC datasource and its Kafka/HTTP infrastructure. The state change and one outbox row commit in the same local transaction; an in-service relay then delivers at-least-once, so "state changed AND the platform heard it" has no crash window in either direction.
**Use it for:** Emitting an event that must not be lost when the business transaction commits (and must not be emitted when it rolls back) — replacing any hand-rolled "save, then publish" dual write.
**Key API:** `OutboxWriter.append(aggregateType, aggregateId, eventType, destination, payload)` plus `+headers` and `+clientProfile, headers` overloads and the request-shaped `append(OutboxAppend)` (`OutboxAppend.of(...)` + `withHeaders`/`withClientProfile`/`withReleaseAt`/`withReference`); SPI `OutboxPublisher` (`supports`/`publish`, first match wins) and `OutboxClientProfileResolver` (named authenticated `RestClient`s); `OutboxRelayedListener` for post-relay bookkeeping; `OutboxMaintenanceService.prune()` (alias `pruneRelayed()`) / `unpark(id)` / `cancel(id)`; `OutboxEvent`, `OutboxRowView`, `OutboxStateFilter` (`PENDING`/`PARKED`/`RELAYED`/`CANCELLED`); `OutboxArchRules.consumersUseOnlyTheSeams()`. Since **1.9.0: LIVENESS LEASES, DATABASE CLOCK, BOUNDED CLAIM** (the relay invariants suite) — a heartbeat thread per pod (`opentmf-outbox-heartbeat`) renews the lease of every send in flight up to the send's bound (the larger of its lease and its send timeout: `send-timeout`, or `OutboxPublisher.sendTimeout(event)`) and interrupts a send still running at its bound once. A lapsed lease on a row whose send was under way (`sending_since`, changeset 007) is booked as a failed attempt (`OutboxLeaseLapsedException`); a lapse on a row held unsent costs nothing. Anything a publisher, booking hook or relayed listener throws is a failed attempt, an `Error` included (`OutboxSendError`). Time is the database's: `OutboxClock` (a replaceable bean) is the JVM clock plus an offset measured against `clock_timestamp()` every 30 s, used for every lease, due time, booking and `created_on`. Only a 2xx relays an HTTP row (a 3xx fails, never followed); a row naming an unknown client profile parks with `TerminalOutboxException`. The Kafka publisher awaits its producer's own verdict (`delivery.timeout.ms` + `linger.ms`). The `CONCURRENT` hand-off queue runs only as deep as the live slots start within about a second; changeset 008 rebuilds the two `CONCURRENT` claim indexes on one "open" expression, and the ORDERED claim is native SQL. Since **1.8.0: INDEPENDENT LANES, STRICT UNPARK BODY, PASTE-VERBATIM PATHS** — the ORDERED batch sends on the ORDERED lane's own thread (`opentmf-outbox-ordered`) and the relay thread only claims, so a slow ORDERED receiver no longer stalls the `CONCURRENT` lane (ORDERED keeps one batch in flight per pod, rows one at a time in `id` order). The unpark-by-filter body is read by the library itself, never through the consumer's mapper: `destination`/`reference` take a string or null, `parkedFrom`/`parkedTo` an RFC 3339 date-time with offset or null, anything else is a 400 naming the field. In the OAS fragment every error in the paths is a `$ref`; the library's refusals (`outboxBadRequest`, `outboxRangeNotSatisfiable`, `outboxRowIdOutOfRange`, `outboxRowNotFound`, and the new `outboxInspectBadRequest`, `outboxUnparkConflict`, `outboxCancelConflict`, `outboxUnparkFilterBadRequest`) are marked `x-opentmf-refinable: content` — their `description` and `headers` stay verbatim, their `content` is the consumer's rendering — so a consumer whose errors are not RFC 9457 pastes the paths verbatim. Since **1.7.0: OPS CONTRACT** — the row routes are `{id:\d+}` (`GET /ops/outbox/{id}`, `POST …/{id}/unpark`, `POST …/{id}/cancel`), so a literal sibling segment is never read as a row id. The OAS fragment (`info.version` 1.7.0) is complete when pasted verbatim: every operation names, by `$ref`, the consumer's own 401/403/405/406/503 (415 on the bulk unpark's body), and every error carries `OutboxProblem` (generic RFC 9457, `application/problem+json`) — the toolkit's 400s keep `Tmf630Error`. `limit` declares no `maximum`, matching the clamp to `paging.max-limit`. Components marked `x-opentmf-refinable: true` (the six consumer answers and `OutboxProblem`) may be redefined under the same name; everything else is pasted verbatim. Since **1.6.0: CLAIM CADENCE** — the `CONCURRENT` claim fills a per-lane hand-off queue up to `batch-size` ahead of the sending slots, with one statement for every candidate key's advisory lock and one stamping every lease, whatever the row count. A RELAYED booking is one guarded `update … returning`. A row that waited a tenth of its lease or longer is renewed right before its send, and `max-in-flight` is now the lane's throughput lever (measured 49 → 562 rows/s at 8 slots). Since **1.5.0: PER-AGGREGATE KAFKA ORDER ACROSS PODS** — `opentmf.outbox.kafka.lane: CONCURRENT` (opt-in; default `ORDERED`) keys each Kafka row by `opentmf.outbox.kafka.ordering-key` (`AGGREGATE_ID` default / `NONE`), so one aggregate's rows are never in flight together on any pod while different aggregates relay in parallel; record key and headers unchanged. Since **1.4.0: PER-LANE GAUGES, `?state=` ON THE LIST, CANCEL REFUSES A LIVE LEASE** — `pending`/`in-flight`/`parked`/`relay-lag` carry a `lane` tag (`ordered`/`concurrent`); `GET /ops/outbox?state=pending|parked|relayed|cancelled` (via `@Tmf630PassThrough`); `cancel(id)` throws `OutboxRowInFlightException` (409 on the endpoint) for a row under a live lease. Since **1.3.0: LANES, LEASES AND BOUNDED OPS** — `OutboxPublisher.lane(event)` (`ORDERED` default / `CONCURRENT`, the HTTP publisher's), `orderingKey(event)` (never two in flight per key, across pods via a PG advisory xact lock), `lease(event)`, `deliver(event)` and `onBooked(event, OutboxBooking)` (the publisher's own DB write, in the booking transaction for every outcome); `OutboxMaintenanceService.pruneExpired()` → `OutboxPruneResult` and `unpark(destination, parkedFrom, parkedTo, reference)` → `OutboxUnparkResult` (set-based, bounded, `moreTo*` flags); `OutboxOpsOpenApi.fragment()` serves the `/ops/outbox` OAS fragment from `META-INF/openapi/opentmf-outbox-ops.oas.yaml`; `OutboxRowView` gains `inFlight`/`claimedUntil`. Since **1.2.0: PER-PUBLISHER FAILURE POLICY, PRIVATE REFERENCE, ONBOARDING** — `OutboxPublisher.maxAttempts(event)` (0 = library `max-attempts`), `backoff(event, attempt)` (null = library backoff) and `onExhausted(event)` → `ExhaustionOutcome.PARK` (default) or `DROP` (stamps `relayed_on`, keeps `last_error`, counts `opentmf.outbox.dropped{destination}`, fires no relayed listener); a publisher throws `TerminalOutboxException` to reach the exhaustion outcome at once. Parking is an explicit `parked_on` stamp. `withReference(...)` stores a private per-row `reference` (≤128 chars, filterable on the ops list, never sent by either publisher — headers are the wire, the reference is private). `OutboxHeaders` exposes the relay header names and `idempotencyKey(serviceName, id)`, a cross-service contract. `GET /ops/outbox/state/{state}` (`/ops/outbox/parked` is its alias); changeset 003 onboards a pre-library `outbox` table. Since **1.1.0: SCHEDULED SENDS + CANCEL** — `withReleaseAt(instant)` holds a row until then (frozen at write; a backoff never moves it); `cancel(id)` / `POST /ops/outbox/{id}/cancel` cancels a row that is neither relayed nor cancelled (cancelled rows stay for audit and prune like relayed ones).
**Config:** prefix `opentmf.outbox` (all optional): `sweep-interval=5s`, `batch-size=100`, `max-attempts=10`, `backoff-base=5s`, `backoff-factor=2`, `backoff-cap=10m`, `retention=7d`, `send-timeout=10s`, `ops-endpoints=true`. Autoconfig `OutboxAutoConfiguration` (unconditional — no `DataSource` guard; a JPA datasource is a hard requirement and its absence fails boot by name). One table, `OUTBOX`, from the bundled changelog — include it **by reference**: `<include file="db/changelog/opentmf-outbox.sql" relativeToChangelogFile="false"/>`. Since **1.9.0:** `http.connect-timeout=10s`, `http.read-timeout` (default: the larger of `lease` and `send-timeout`, less a tenth — 108 s with the defaults; when set it must be below that larger value, checked at startup) for the plain HTTP client; a profile's client keeps its own timeouts. Since **1.6.0:** no property added or renamed, but `batch-size` also sizes the `CONCURRENT` hand-off queue and `concurrent.max-in-flight` sets the lane's throughput (size the connection pool above `max-in-flight` + 2). Since **1.5.0:** `kafka.lane=ORDERED` (`CONCURRENT` for per-aggregate order across pods), `kafka.ordering-key=AGGREGATE_ID` (`NONE`), `kafka.lease=15s` (must exceed `send-timeout`). Since **1.3.0:** `lease=2m` (CONCURRENT), `ordered.lease=15s` (must exceed `send-timeout`), `concurrent.max-in-flight=8` (per pod), `shutdown-grace=10s`, `metrics-refresh=15s`, `maintenance.batch-size=5000`, `maintenance.time-budget=10s`; changesets 004/005 add `claimed_until`/`lane`/`ordering_key` and eight partial indexes built `CONCURRENTLY`.
**Snippet:**
```java
@Transactional
public void recordOutcome(String id, Outcome outcome) {
  repository.save(...);                                    // state change

      "comm.outcome.v1", "comm.outcome.v1", outcome);      // same transaction

```
**Gotchas:** `append` is propagation **`MANDATORY`** — calling it outside a transaction fails fast, by design (a dual write cannot compile into existence). The payload is serialized **at write time**: the event is a fact frozen at commit, never re-read later. Destination routing is by shape — anything that is not an `http(s)://` URL is a Kafka topic. Delivery is at-least-once; dedupe on `x-idempotency-key` (`<spring.application.name>:outbox:<id>`). At `max-attempts` a row **parks** — excluded from claims, never auto-pruned, unparking is a deliberate ops action (since 1.2.0 a publisher can set the budget and choose `DROP` per row). The `/ops` endpoints ship **no security of their own** — the consumer must gate them as admin-class (payloads and `last_error` travel there). `tmf630-toolkit-all` is optional: without it the `/ops` controller is not registered at all (the `OutboxMaintenanceService` API is unaffected). Kafka/web deps are optional too — ⚠ **1.2.1 upgrade:** before 1.2.1 that was true only on paper for Kafka: a consumer without `spring-kafka` failed at context start with `NoClassDefFoundError: org/springframework/kafka/core/KafkaTemplate` (the auto-configuration named the type in a bean-method signature); from 1.2.1 a Kafka-less consumer starts with the HTTP publisher only, a web-less one with the Kafka publisher only, and a workaround that added `spring-kafka` + excluded `KafkaAutoConfiguration` can be dropped. The nested publisher configurations are deliberately not `@Configuration`, so a scan root covering `org.opentmf.outbox` does not register them out of order. The ArchUnit seal rule needs ArchUnit ≥ 1.5.0 on Java 25 bytecode — older ASM parses nothing and the rule silently checks **nothing**. ⚠ **1.2.0 upgrade:** the ops controller answers 404/409/400 through Spring's `ResponseStatusException`, so a global exception handler that swallows `ErrorResponse` turns them into 500 — fix the handler in the same change (the dnms template's `GlobalExceptionMapper` fix). Attempts alone no longer park a row: test fixtures that seed parked rows must set `parkedOn`, and a row parked under 1.1.0 (no stamp) becomes claimable again and re-parks with the stamp on its next failure. `OutboxRowView` and `OutboxAppend` gained record components, so their canonical constructors changed — use `of` and the withers. A held row counts as pending but not as relay lag. ⚠ **1.3.0 upgrade:** a publisher that wrote to its own tables inside `publish` must move that write to `onBooked` — `publish` now runs in NO transaction, so such a write silently stops being atomic with `relayed_on`. HTTP rows no longer keep `id` order against Kafka rows or other receivers (same receiver: happy path only). A crash between send and booking now redelivers after the lease lapses (≤15 s ORDERED, ≤2 min CONCURRENT), not on the next sweep. Gauges read NaN until the first refresh — alert on `opentmf.outbox.metrics-age`, not on a NaN `pending`. A caller of the prune/unpark endpoints must loop while `moreToPrune`/`moreToUnpark` is true. The first start runs eight `CONCURRENTLY` index builds (~2.3 s per million rows): widen the startup probe. During a 1.2.x/1.3.0 rolling overlap per-key order is not guaranteed (no duplicates). ⚠ **1.4.0 upgrade:** the four gauges become two series each (`lane` tag) — a bare-name panel shows two lines and a sum-based alert must use `sum without (lane)` (`max without (lane)` for `relay-lag`) to keep its 1.3.0 meaning. A cancel of an in-flight row now answers 409 instead of success — callers that cancel must handle the refusal and retry after the send is booked. Changeset 006 drops `ix_outbox_open_since` and builds three indexes `CONCURRENTLY` on first start. ⚠ **1.5.0 upgrade:** with several pods the default `ORDERED` Kafka lane can deliver one aggregate's rows out of order — set `kafka.lane: CONCURRENT` for per-aggregate order. The lane is stamped at append: rows pending at the switch drain on `ORDERED`, and order is complete only once every appending pod runs 1.5.0 with the setting. On `CONCURRENT`, Kafka rows share `concurrent.max-in-flight` (8 per pod) with HTTP rows — raise it if a pod relays many of both. ⚠ **1.6.0 upgrade:** `opentmf.outbox.in-flight` (lane `concurrent`) now also counts rows waiting in the hand-off queue, up to `batch-size` more per pod, so an alert threshold tuned to `max-in-flight` fires under ordinary load. Each sending slot holds a connection while it books, so size the connection pool above `max-in-flight` + 2. `CONCURRENT` bookings and renewals now run at the application's default isolation, not a READ COMMITTED pin; a non-READ-COMMITTED default costs a serialization-error retry path on a lease race, never a wrong booking. Shutdown drops the rows still queued unsent, and they redeliver once their leases lapse. ⚠ **1.8.0 upgrade:** size the connection pool above `concurrent.max-in-flight` + **3** (was + 2) — the relay thread's claim and an ORDERED booking can hold a connection at the same moment. Shutdown gives the relay thread, the ORDERED batch and the CONCURRENT sends `shutdown-grace` each, in turn. An unpark-by-filter body with a wrongly typed field (`{"destination": false}`, a number, an array, a date-time without offset) now answers 400 where a coercing mapper made it a 200; a sent offset is kept as sent instead of normalised to UTC. Re-paste the fragment: four inline error responses became `$ref`s, so the paths changed. A drift test written for 1.7.0 keeps passing for a consumer that refines only the `true` components; one that refines a refusal's content adds the `content` rule (compare those components by description and headers). ⚠ **1.9.0 upgrade:** size the pool above `concurrent.max-in-flight` + **4** (the heartbeat's renewal can hold a connection too). Lapses now count against the publisher's budget: a send that routinely outlives its lease parks or drops instead of being re-sent every lease — declare a long send with `sendTimeout(event)`. A receiver slower than the HTTP read timeout (108 s by default) fails the attempt, and so does one that answers with a redirect. A row naming a client profile the resolver does not know parks (before, it went out through the plain client without the profile's authentication). The cancel 409 now says the row is claimed (queued or sending); re-paste the fragment for its description. ⚠ **1.7.0 upgrade:** every valid request answers as before, but a non-digit id segment now matches no route — `/ops/outbox/state`, `/ops/outbox/-1` or `POST /ops/outbox/abc/cancel` answer **404** where they answered 400, and `GET /ops/outbox/unpark` is a **405** (`OPTIONS` names POST alone). Re-paste the fragment: the hand-layered 401/403/405/406/415/503 on the ops routes are now part of it, and a named waiver for the `limit` bound or for `/ops/outbox/unpark` can go. A drift test compares paths exactly and components exactly unless marked refinable. The library's own toolkit dependency moved to 3.5.1, already the BOM's pin; its undeclared-query-parameter guard stays off until a consumer switches it on.
**Maven:** `org.opentmf.util:opentmf-outbox-service` (BOM-managed).

**Snippet:** `PUT localhost:1080/mockserver/expectation` with `httpResponseClassCallback.callbackClass = …DynamicPostCallback`.
**Gotchas:** Jackson 3 only; XML/dashboard/proxy/templating stripped out. ### opentmf-mockserver-test-support
**What:** Fluent JUnit 5 test-support layer over `opentmf-mockserver` (new sibling artifact in the 2.1.9 multi-module split): starts an in-process MockServer on a random free port, registers the server's `Dynamic*Callback`s, mints RSA-signed Keycloak-shaped JWTs, and redirects Spring properties at the mock.
**Use it for:** Replacing hand-rolled `ClientAndServer` + `Dynamic*Callback` + JWKS + `@DynamicPropertySource` IT glue. Works for plain JUnit, Spring Boot ITs, and non-JUnit harnesses (Cucumber/E2E) via `start()`/`stop()`.
**Key API:** Package `org.opentmf.mockserver.testsupport`. `MockServerSupport` (`create()` per-class / `shared()` JVM-singleton; `start/stop`, `port()`, `baseUrl()`, `client()`, `keepExpectationsBetweenTests()`, `expect(HttpRequest,HttpResponse)`, `clear(Registration...)`, `redirectApiClients(registry, ids…)`, `redirectHttpClients(registry, ids…)`, `redirectJwks(registry[, realm])`, `token/tokenFor/bearerHeader`) — implements `BeforeAllCallback`/`AfterAllCallback`/`AfterEachCallback`. Builders: `tmf(apiClientId)` → `TmfMockBuilder.post/get/getList/put/delete/jsonPatch/mergePatch/jsonPatchCollection/crud(path)`; `stub()` → `StubBuilder.get/post/put/delete/method` + `limit/pathParam/queryParam/header/jsonBody` → `respondJson/respondStatus/respondDelayed/respondSequence`; `verify()` → `VerifyBuilder.get/post/put/delete/method` + `withHeader/withQueryParam/withJsonBody` → `times/atLeast/atMost/never/once`; `Registration.id()/ids()/clear()`; `OidcMockSupport.realm/clientId/expiresInSeconds/token/tokenFor/jwksPath/jwksUri/jwksJson/registerJwksEndpoint` (`DEFAULT_REALM="realm1"`, `DEFAULT_CLIENT_ID="opentmf-mockserver"`, `DEFAULT_EXPIRES_IN_SECONDS=3600`).
**Config:** No properties of its own — it *writes* them: `opentmf.api-clients.<id>.base-url` (+ `context-path` → `""`), `opentmf.http-clients.<id>.base-url`, `opentmf.security.jwk-set-uri` → `<baseUrl>/realms/<realm>/protocol/openid-connect/certs`. Server behavior/env vars are `opentmf-mockserver`'s.
**Snippet:**
```java
@SpringBootTest
class DocumentServiceIT {
  @RegisterExtension static MockServerSupport mock = MockServerSupport.shared();

  @DynamicPropertySource
  static void redirect(DynamicPropertyRegistry r) {
    mock.redirectApiClients(r, "onedms");
    mock.redirectJwks(r);
  }

  @Test void archives() {
    mock.tmf("onedms").crud("/document");
    mock.stub().get("/kba/{key}").pathParam("key", "42").respondJson(200, "{\"v\":42}");
    // exercise service, e.g. with header Authorization = mock.bearerHeader("writer")
    mock.verify().post("/document").once();
  }
}
```
**Gotchas:** `afterEach` calls `server.reset()` — it wipes **all** expectations, including the JWKS endpoint `redirectJwks` registers once at property-resolution time and anything registered in `@BeforeAll`; register per `@Test` or call `keepExpectationsBetweenTests()`. The constructor is private: only `create()`/`shared()`; `shared()`'s reset is server-wide, so it is unsafe with test classes running in parallel (use `create()`). `limit(N)` applies to the next `respond*` only and is a no-op with `respondSequence(...)` (which pins one call per element); calling a matcher or `respond*` before a verb-starter throws `IllegalStateException`. `tmf(...).get/put/delete/jsonPatch/mergePatch` append the regex `/[^/]+` to the path, and `crud(path)` omits `jsonPatchCollection`; the `apiClientId` argument is only a label and does not affect the URL. JUnit, `spring-test`, and `spring-boot-test` are `provided`+`optional` — non-Spring consumers get the rest of the module but must not call `redirect*`.
**Maven:** `org.opentmf.mockserver:opentmf-mockserver-test-support` (test scope; BOM-managed since opentmf-versions 2.1.14).
